## Затверджена модель дублювання

Scaler має створювати в тій самій кампанії:

- новий AdSet;
- нове Page Video;
- новий Creative через `object_story_spec.video_data`;
- нове оголошення у новому AdSet;
- без передачі `object_story_id` існуючої публікації;
- у статусі `PAUSED` під час тестів.

Справжню нову копію підтверджує одночасне виконання умов:

- `new_ad_id != source_ad_id`;
- `new_creative_id != source_creative_id`;
- `copied_adset_id != source_adset_id`;
- нове оголошення належить новому AdSet;
- нове оголошення використовує новий Creative;
- Creative створений через `object_story_spec`, а не `object_story_id`;
- новий Creative використовує новий `video_id`;
- у Ads Manager вибрано «Створити оголошення», а не «Використовувати існуючу публікацію».

## Результати тестів

### v26.3 — відхилено

- Новий AdSet було створено.
- Creative створювався через `object_story_id`.
- Ads Manager показував «Використовувати існуючу публікацію».
- Такий спосіб не відповідає задачі дублювання оголошення.

### v26.4 — структура нового дубля підтверджена

Джерело:

- AdSet: `120247989505660301`
- Ad: `120247989505540301`
- Creative: `1785909172594984`
- root video: `2189511635226791`

Створено:

- AdSet: `120248233771070301`
- Ad: `120248233772070301`
- Creative: `1471180001441578`
- Page Video: `1848696159451925`

Підтверджено:

- усі структурні ID нові;
- новий Ad знаходиться у новому AdSet;
- новий Ad використовує новий Creative;
- Creative створено через `object_story_spec.video_data`;
- `object_story_id` існуючої публікації у запит Creative не передавався;
- текст, CTA, URL і Pixel збігаються;
- Ads Manager показує «Створити оголошення»;
- оголошення створено без API-помилки.

Важливо: загальний `true_duplicate_ok` у звіті v26.4 дорівнює `false`, бо API-аудит знайшов одну розбіжність AdSet:

- у джерелі `targeting_automation.individual_setting` містить `age: 1` і `gender: 1`;
- у копії це вкладене поле відсутнє;
- явні `age_min`, `age_max`, гео, плейсменти та платформи у звіті збережені.

Після v26.5.2 користувач перевірив новий AdSet в Ads Manager і підтвердив, що
налаштування групи правильні. Тому відсутність `individual_setting` у повторному
GET-відгуку класифікуємо як UI-підтверджену нормалізацію readback для цього
сценарію. Розбіжність залишається видимою у JSON як warning, але сама по собі
не блокує тест.

### v26.5.1 — відхилено: Meta вимагає мініатюру

Тест навмисно не передавав `image_url` або `image_hash`, щоб перевірити,
чи залишить Meta вибір мініатюри в режимі `Авто`.

Результат:

- нове Page Video створено: `1364327572519044`;
- новий AdSet створено: `120248234118690301`;
- Creative не створено;
- Meta повернула `code=100`, `subcode=1443226`;
- вимога Meta: передати `image_hash` або `image_url` у `object_story_spec.video_data`.

Висновок: для цього сценарію створення нового Creative через
`object_story_spec.video_data` режим без передавання мініатюри технічно не
працює. Це підтверджено фактичним API-викликом, а не припущенням.

### v26.5.2 — перший запуск не тестував дублювання

Перший запуск було виконано з неправильним source AdSet:

- передано `120248234118690301` — залишковий порожній AdSet, створений v26.5.1;
- правильне джерело — `120247989505660301`;
- у переданому AdSet знайдено `0` оголошень;
- скрипт зупинився на перевірці джерела з повідомленням
  `Expected exactly 1 ad in source adset; got 0`;
- нові AdSet, Page Video, Creative або Ad у цьому запуску не створювалися;
- `cleanup: []` є правильним результатом, бо очищувати після цього запуску нічого.

Це помилка вхідного ID, а не помилка токена, дозволів, Meta-generated thumbnail
або механізму дублювання. Результат гіпотези v26.5.2 залишається невідомим до
повторного запуску на правильному джерелі.

### v26.5.2 — дубль створено, гіпотезу мініатюри відхилено

Повторний запуск виконано з правильним source AdSet `120247989505660301`.

Створено:

- Page Video: `1031980492959285`;
- AdSet: `120248234293180301`;
- Creative: `1367411501557215`;
- Ad: `120248234294370301`.

Підтверджено:

- новий Ad знаходиться у новому AdSet;
- новий Ad використовує новий Creative;
- Creative створено через `object_story_spec` без `object_story_id`;
- текст, CTA, URL і Pixel збережені;
- помилок доставки після створення немає;
- налаштування AdSet в Ads Manager користувач перевірив як правильні.

Результат перевірки мініатюри:

- скрипт не завантажував власну обкладинку і не змінював `is_preferred`;
- `image_url` був узятий з кадру, автоматично згенерованого Meta;
- Ads Manager усе одно показав режим `Вручну`;
- отже, походження кадру не зберігає режим `Авто`, якщо `image_url` явно
  передано при створенні Creative.

Висновок: гілка ручного створення нового Creative через `object_story_spec`
не дає потрібної поведінки мініатюри. Наступний тест переходить на нативний
Ad Copies API.

### v26.6 — поточна гіпотеза

- AdSet копіюється через `POST /{adset_id}/copies`;
- Ad копіюється через `POST /{source_ad_id}/copies` у новий AdSet;
- creative-параметри не передаються;
- `object_story_id`, `image_url` та `image_hash` не передаються;
- Meta сама вирішує, чи повторно використати незмінний Creative або створити
  новий Creative;
- обов'язково має бути новий Ad ID у новому AdSet;
- у UI перевіряємо `Створити оголошення` та мініатюру `Авто`.

## Поточний наступний крок

1. Замінити на GitHub `fb_duplicate_test.py` версією v26.6 та запустити з
   початковим source AdSet `120247989505660301`.
2. Перевірити в Ads Manager:
   - режим оголошення — «Створити оголошення»;
   - мініатюра — `Авто`;
   - текст, CTA, URL, Pixel і статус оголошення.
3. Надіслати Telegram-повідомлення, JSON
   `duplicate_test_v26_6_native_ad_copies_report.json` і скрин мініатюри.
4. Не переходити до production `fb_scaler.py`, доки v26.6 не підтвердить
   нативний дубль і режим мініатюри `Авто`.
